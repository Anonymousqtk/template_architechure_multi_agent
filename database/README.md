# AUTH-001 database (PostgreSQL 18)

High-risk schema changes. `001` retains the reviewed initial schema; `002` binds sessions to organizations, persists shared throttling counters and records invitation delivery status. All UUIDs are generated by the application. Only SHA-256 token/session hashes are stored. No raw token outbox exists.

Run `node database/test-migrations.mjs` from the repository root. This creates a fresh PostgreSQL cluster in OS temporary storage, binds localhost on an available port, applies sorted migrations, verifies real constraint violations and fixture rollback, stops the cluster, then removes only its own temporary directory. `PG_BIN` can select a PostgreSQL binary directory. Windows defaults to PostgreSQL 18. The shell entrypoint `database/test-migrations.sh` invokes the same test for CI; Unix PostgreSQL tools must be on PATH. Trust authentication is limited to the disposable test cluster and must never be used for deployment.

The same ordered migration SQL can be reviewed and applied to a new development database with `psql -X -v ON_ERROR_STOP=1 -f database/migrations/001_auth_invitation_schema.sql` followed by `002_auth_controls.sql`. Connection selection is the operator's responsibility; these commands are instructions, not automatic production execution. Do not rerun 002: it is a forward migration, with no silent IF NOT EXISTS masking schema drift. A production migration ledger and approved deployment process remain release prerequisites.

Rollback/restore: each migration is transactional; SQL errors roll back that migration. For an unshipped disposable environment, discard and rebuild the database. After accepting real users, restore an approved pre-migration backup or ship a separately reviewed forward repair; do not drop authentication tables or organization columns. No destructive rollback script is supplied. New tables/indexes take DDL locks; adding the non-null session organization column assumes an empty initial database. Existing sessions require a separately reviewed backfill migration before 002. No production migration, admin bootstrap or deployment was executed.

Backend transaction contract: lock invitation/reset rows before validity checks and mutations; commit token consumption together with membership creation/password update. Resend must replace token_hash atomically and revoke the former token. Authorize organization and active membership on every request. `auth_rate_limits` keys should be SHA-256 hashes of IP/account/recipient/organization dimensions; atomically upsert counters and prune old windows. Audit metadata must exclude passwords, raw tokens, and session identifiers. Schema constraints supplement, rather than replace, these application checks.
`MIGRATION_TEST_BACKEND=true` additionally runs the existing backend Vitest coverage command against the same disposable database (install backend dependencies first). Migration-only execution remains the default.

AUTH-002 migration003 adds MANAGER and a tenant-bound manager assignment without replacing AUTH-001 tables. Disposable verification seeds an existing AUTH-001 account before003, asserts its identity/hash/role/status are unchanged afterward, then checks invalid roles, self assignment and cross-organization FK rejection. Migration003 takes DDL locks on memberships; do not apply to production without human-reviewed migration/backup plan. Rollback: restore approved backup or reviewed forward repair; no destructive rollback is supplied.
